# Plan: Embedded Protocluster Search

## Goal

Keep SQLite as the authoritative catalog for files, records, byte offsets, and metadata. Add Tantivy as a rebuildable embedded search index through the existing PyO3 extension.

Implement the feature in three independently testable stages:

1. Build and query the index directly from Python.
2. Expose protocluster search through the Flask backend.
3. Add frontend search results and record-to-protocluster navigation.

Each Tantivy document represents one protocluster. Therefore, every clause in a query such as:

```text
pfam:PF00512 AND pfam:PF00513
```

must match within the same protocluster document.

## Source Format Compatibility

The demo JSON files used to design and test extraction were generated by
antiSMASH 8.0.2, which is the baseline format for the extractor. Any valid
antiSMASH 8.x JSON file should generate the same search-document structure,
regardless of its minor or patch version.

Read and retain the top-level `version` value for diagnostics, but do not reject
a file solely because its declared major version is not 8. For antiSMASH 7.x,
9.x, or another version, optimistically run the v8-compatible extraction path.
Accept the file when the required record, feature, location, and protocluster
qualifier structures can be read and the generated documents pass validation.
Only raise a clear compatibility error when those required structures are
missing or incompatible, and include the declared antiSMASH version and the
failing field or structure in the error. Keep the search-document schema
independent of optional antiSMASH fields so documents remain stable when
qualifiers are absent or additional qualifiers appear.

## Search Document

Use a stable document key derived from:

- Source file path
- Record ID
- Region number
- Protocluster number

Store the SQLite parent `records.id` so backend results can later be hydrated without relying on source paths alone.

Suggested fields:

| Public field | Document values | Search behavior |
| --- | --- | --- |
| `pfam` | PFAM accessions | Exact, case-normalized, multi-valued |
| `pfam_name` | PFAM names and descriptions | Full text, multi-valued |
| `organism` | Organism name | Full text |
| `gene` | Gene names and locus tags | Exact, case-normalized, multi-valued |
| `product` | Protocluster product | Full text, single-valued |
| `category` | Protocluster product category | Full text, single-valued |
| `record` | Parent record ID | Exact, case-normalized |
| `region` | Parent region number or ID | Exact |
| `protocluster` | Protocluster number or ID | Exact |

In antiSMASH, each `Protocluster` has one `product` string and one
`product_category` string. Candidate clusters and regions aggregate values from
multiple contained protoclusters, so their serialized `product` and category
metadata can be multi-valued. Do not copy those aggregate lists into an
individual protocluster search document.

Also store these non-search or display fields:

- Stable document key
- SQLite parent record ID
- Source path
- Input filename
- Record ID
- Region number
- Protocluster number

Normalize versioned PFAM accessions during extraction. For example, store `PF00512.28` as `PF00512` in the `pfam` field.

Unqualified terms should search all public fields, including exact identifier fields. Results should be ordered by Tantivy relevance score with the stable document key as a deterministic tie-breaker.

## Query Language

Support:

- `AND`, `OR`, and `NOT`
- Parentheses and normal Boolean precedence
- Field-qualified terms
- Quoted phrases for analyzed text
- Unqualified terms across default fields

Examples:

```text
pfam:PF00512 AND pfam:PF00513
pfam_name:"His Kinase"
organism:Amycolatopsis
(pfam:PF00512 OR pfam:PF00513) AND organism:Amycolatopsis
organism:Amycolatopsis NOT pfam:PF00513
```

Invalid syntax must produce a structured parse error with the best available character position. It must not silently become an empty result or literal query.

## Stage 1: Python Indexer and Searcher

The first stage must be usable without Flask or Vue. Its purpose is to experiment with document extraction, analyzers, query syntax, and ranking directly from Python.

### 1. Extract protocluster documents

Add a Python extraction helper in `backend/bgc_viewer/preprocessing.py` that consumes one already-parsed antiSMASH record and emits compact protocluster documents.

For each protocluster:

1. Find its containing parent region.
2. Collect genes and PFAM domains whose genomic intervals overlap it.
3. Use half-open interval overlap semantics.
4. Deduplicate values in multi-valued fields.
5. Remove PFAM version suffixes.
6. Exclude sequences, translations, and other large payloads.
7. Skip malformed features defensively and report extraction counts or errors.

Add fixtures covering:

- Multiple regions in one record
- Multiple protoclusters in one region
- PFAM domains inside and outside the protocluster
- Duplicate field values
- Versioned PFAM accessions
- Missing qualifiers
- Boundary-touching intervals
- The demo antiSMASH 8.0.2 format
- At least one additional antiSMASH 8.x fixture when available
- Successful v8-compatible extraction from structurally compatible 7.x and 9.x fixtures
- A clear compatibility error for a non-v8 file with an incompatible required structure

### 2. Add Tantivy to the Rust extension

Update:

- `backend/rust_extensions/Cargo.toml`
- `backend/rust_extensions/src/lib.rs`

Keep the existing `scan_records()` binding and add the search functionality to the same `bgc_scanner` extension.

Register separate analyzers:

- Raw whole-value tokenization plus lowercase normalization for exact identifiers
- Unicode word tokenization plus lowercase normalization for human-readable text

Exact and analyzed fields must live in the same Tantivy document so one nested Boolean query can combine both types.

### 3. Expose a Python API through PyO3

Expose a stateful writer that can:

1. Create an index in a temporary directory.
2. Accept one compact document at a time.
3. Commit the index.
4. Atomically publish the completed index directory.

Streaming one document at a time prevents Python from retaining a converted copy of the full source corpus.

Expose a reusable reader that can:

1. Open an existing index.
2. Parse the public query language.
3. Search with offset and limit.
4. Return the total hit count.
5. Return stored identities, display fields, and scores.
6. Return structured query parse errors.
7. Release the Python GIL while executing the search.

Use public field aliases rather than exposing internal Tantivy schema names.

### 4. Add a Python development CLI

Add a small script or module CLI under the backend package with commands equivalent to:

```text
build-index SOURCE_DIRECTORY INDEX_DIRECTORY
search INDEX_DIRECTORY QUERY
```

The search command should print:

- Score
- Source path
- Record ID
- Region number
- Protocluster number
- Useful display metadata

This CLI is the primary manual experimentation surface for Stage 1.

### 5. Test Stage 1

Add Rust and Python tests for:

- Document extraction and interval overlap
- Multi-valued exact fields
- PFAM version normalization
- Optimistic cross-version extraction and structural compatibility validation
- Exact versus analyzed matching
- Case normalization
- Boolean precedence
- Parentheses and nesting
- Negation
- Phrase searches
- Unqualified searches
- Ranking and stable tie-breaking
- Pagination and total counts
- Commit, close, and reopen
- Malformed query errors

Stage 1 is complete when a user can build, close, reopen, and query an index entirely from Python.

Record index size, build throughput, and cold and warm query latency on representative data before moving to Stage 2.

## Stage 2: Backend API

Stage 2 begins only after the Python search API and query behavior are stable.

### 1. Integrate preprocessing

Extend `preprocess_antismash_files()` to:

1. Create a Tantivy writer beside the requested SQLite database.
2. Stream extracted protocluster documents while processing records.
3. Commit SQLite and Tantivy.
4. Atomically publish the derived search index only after successful processing.
5. Remove temporary index data after failure without removing a previously valid index.

Store the following in SQLite metadata:

- Search schema version
- Search index version
- Search index location

The supported update model is build once and query many. Incremental indexing and live writes are deferred.

### 2. Add a dedicated search endpoint

Keep `/api/database-entries` and `get_database_entries()` for existing record browsing.

Add a dedicated endpoint:

```text
GET /api/search?q=QUERY&page=1&per_page=20
```

A dedicated endpoint avoids conflating record-level browsing with protocluster-level search results.

The response should contain:

- Ranked protocluster hits
- Total hit count
- Page and page size
- Tantivy score
- Source path
- Parent record ID
- Region number
- Protocluster number
- Display metadata

### 3. Hydrate results from SQLite

Use the stored parent `records.id` to fetch additional record metadata from SQLite in one bulk query.

Preserve Tantivy result order after hydration. Do not reorder by filename or database row ID.

### 4. Manage reader lifecycle

Cache and reuse a Tantivy reader for the currently selected database. Invalidate and reopen it when preprocessing publishes a new index.

Report distinct errors for:

- Invalid query syntax
- Missing index
- Corrupt index
- Incompatible schema version

SQLite record browsing must continue to work when the derived Tantivy index is unavailable.

Return HTTP 400 for invalid syntax with a stable JSON payload containing an error code, message, and input position.

### 5. Test Stage 2

Add backend tests for:

- Index publication and failure cleanup
- Reader reopening and cache invalidation
- Query URL encoding
- Ranked pagination
- SQLite hydration order
- Invalid-query responses
- Missing and stale indexes
- Existing record browsing without a search index

Stage 2 is complete when protocluster searches work through Flask without frontend changes.

## Stage 3: Frontend Search and Navigation

Advanced search initially applies only to preprocessed backend datasets. Browser-loaded JSON and GenBank providers retain their existing basic search behavior.

### 1. Add the API contract

Update:

- `frontend/src/services/dataProviders/BGCViewerAPIProvider.ts`
- `frontend/src/services/dataProviders/types.ts`

Call `/api/search` for advanced backend searches and map the response into a protocluster search-result type.

Each result must carry:

- Parent entry ID
- Record ID
- Filename
- Region number
- Protocluster number
- Organism
- Products and categories
- Score

### 2. Display protocluster results

Update `frontend/src/components/RecordListSelector.vue` to:

- Display multiple protocluster hits from the same parent record
- Show enough organism, product, category, region, and cluster context to distinguish them
- Display structured query errors beside the search input
- Keep the previous valid result set visible when a new query has a syntax error

### 3. Navigate to the hit

Extend the selection payload through `RecordListSelector.vue` and `frontend/src/App.vue` with optional region and protocluster numbers.

The selection sequence is:

1. Load the parent record.
2. Select the parent region.
3. Focus and highlight the matching protocluster.

Reuse `RegionViewerContainer`'s existing `initialRegionId` mechanism to select `region_{region_number}`.

Add an `initialProtoclusterNumber` prop to `RegionViewer.vue`. After the selected region tracks are built:

1. Locate the protocluster annotation by qualifier.
2. Invoke the existing annotation selection and highlighting path.
3. Scroll or zoom the protocluster into view.

An ordinary record selection must clear any stale region or protocluster target.

### 4. Test Stage 3

Add frontend tests for:

- API query forwarding
- Structured error mapping
- Multiple cluster hits belonging to one parent record
- Record-to-region-to-protocluster target propagation
- Focus after asynchronous region loading
- Clearing stale focus after an ordinary record selection

Stage 3 is complete when selecting a search hit opens its parent record, selects its parent region, and focuses the correct protocluster.

## Final Decisions

- Tantivy is selected because arbitrary nested Boolean expressions must combine differently analyzed fields in one engine.
- SQLite remains authoritative; Tantivy is local, embedded, disposable, and rebuilt from source JSON.
- No Elasticsearch or other external search service is introduced.
- One Tantivy document and one search hit represent one protocluster.
- The demo files establish antiSMASH 8.0.2 as the extraction baseline. Other
	versions use the same v8-compatible extractor and are accepted whenever their
	required structures validate; the version number alone is not a rejection
	criterion.
- PFAM versions are normalized away for exact searches.
- Unqualified terms search both analyzed human-readable fields and exact identifier fields.
- Results use relevance scoring with a deterministic tie-breaker.
- Stage 1 has no Flask or frontend dependency.
- Incremental indexing, live writes, and advanced search for browser-local providers are out of scope for the initial implementation.
